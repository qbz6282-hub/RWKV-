## 1. 量化的數學：一個區塊就是一個縮放係數

所有 GGUF 量化格式都是同一個套路的變形：

```text
把張量攤平 → 切成固定大小的區塊 → 每個區塊存「一個（或幾個）縮放係數 + 一堆低位元整數」
```

以 **Q4_0** 為例，一個區塊是 32 個數值：

```text
┌─────────┬──────────────────────────────────┐
│  scale  │  32 個 4-bit 有號整數             │
│  2 bytes│  16 bytes                        │
└─────────┴──────────────────────────────────┘
   總共 18 bytes / 32 個權重 = 4.5 bit/權重
```

還原公式：

```text
w[i] ≈ q[i] × scale
```

`q[i]` 是 −8..7 的整數，`scale` 是 f16。量化時 `scale = max(|w|) / 7`，
`q[i] = round(w[i] / scale)`。

**關鍵在於「一個區塊」有多大。** 如果整張張量只有一個 scale（per-tensor），
一個離群值就能毀掉整張表；如果 32 個數值一個 scale，災情就只限於那 32 個。
第四節會把這件事量出來。

K-quant 系列（Q4_K 等）再進一步：256 個數值一個 super-block，裡面切 8 個子區塊，
每個子區塊有自己的 6-bit 縮放，而 super-block 層級再存一組 f16 的 `d` 與 `dmin`。
多這一層，同一個位元數下誤差就小一截。

## 2. candle 的型別系統

candle 用 `GgmlDType` 這個 enum 表示所有量化格式，共 15 種。
底下這張表是從 `candle-core/src/quantized/mod.rs` 對出來的，
`code/src/lib.rs` 裡也維護了一份一模一樣的：

| 型別 | 每區塊元素 | 每區塊位元組 | 位/權重 | GGUF 編號 |
|---|---|---|---|---|
| F32 | 1 | 4 | 32.00 | 0 |
| F16 | 1 | 2 | 16.00 | 1 |
| BF16 | 1 | 2 | 16.00 | **30** |
| Q4_0 | 32 | 18 | 4.50 | 2 |
| Q4_1 | 32 | 20 | 5.00 | 3 |
| Q5_0 | 32 | 22 | 5.50 | 6 |
| Q5_1 | 32 | 24 | 6.00 | 7 |
| Q8_0 | 32 | 34 | 8.50 | 8 |
| Q8_1 | 32 | 36 | 9.00 | 9 |
| Q2_K | 256 | 84 | 2.62 | 10 |
| Q3_K | 256 | 110 | 3.44 | 11 |
| Q4_K | 256 | 144 | 4.50 | 12 |
| Q5_K | 256 | 176 | 5.50 | 13 |
| Q6_K | 256 | 210 | 6.56 | 14 |
| Q8_K | 256 | 292 | 9.12 | 15 |

三個容易踩到的點：

1. **BF16 的編號是 30，不是 2。** 這是 GGUF 後來才補的型別，編號沒跟著順序走。
2. **`Q4_0` 不是「4 bit」，是 4.5 bit。** 那 0.5 就是每 32 個權重攤到的 2 bytes 縮放係數。
   同理 Q8_0 是 8.5 而不是 8。
3. **candle 沒有公開 `to_u32()`。** 它是 `pub(crate)`，所以寫 GGUF 時型別編號要自己填。
   這也是為什麼 `code/src/lib.rs` 要維護那張表。

## 3. QTensor 實戰：把誤差量出來

`QTensor` 和 `Tensor` 是兩個完全不同的東西。`Tensor` 有 autograd、有 dtype、
可以隨意 reshape；`QTensor` 只有形狀、量化型別、和一堆位元組，**沒有梯度**。
這件事在文件三會變成一個大問題。

> **順帶一個坑**：`Device::set_seed(42)` 在 CPU 後端會直接報錯
> （`cannot seed the CPU rng with set_seed`），所以 `Tensor::randn` 的結果每次都不一樣。
> 文件要引用固定數字，就只能自己造一個確定性 PRNG——
> `01_qtensor_basics.rs` 裡用 20 行的 xorshift32 + Box-Muller 解決了這件事，
> 順便讓你不用為了「可重現」去拉 `rand` 依賴。

先看量化與反量化：

```rust
// 造一個 768×768 的常態分佈矩陣。768 是 0.1B 的 hidden_size，
// 同時也是 Q4_0（32）與 Q4_K（256）的區塊大小的公倍數。
let w = Tensor::randn(0f32, 1f32, (768, 768), &dev)?;

// 量化：Tensor → QTensor。內部會先轉 f32 再 flatten_all()，
// 所以「形狀」只用來檢查能不能被 block_size 整除，真正的量化沿著攤平後的一維陣列切。
let qt = QTensor::quantize(&w, GgmlDType::Q4K)?;

// 反量化：QTensor → Tensor。這一步是有損的，回來的不會等於原值。
let back = qt.dequantize(&dev)?;

// 實際佔用位元組 = 區塊數 × 每區塊位元組，不是元素數 × 位元。
let bytes = qt.storage_size_in_bytes();
```

實測（`cargo run --release --bin 01_qtensor_basics`，種子固定為 42，每次跑數字完全一致）：

| 型別 | 大小 | 位/權重 | 壓縮比 | RMSE | 餘弦相似度 |
|---|---|---|---|---|---|
| F32 | 2.25 MiB | 32.00 | 1.0x | 0.00000 | 1.000000 |
| F16 | 1.12 MiB | 16.00 | 2.0x | 0.00021 | 1.000002 |
| BF16 | 1.12 MiB | 16.00 | 2.0x | 0.00166 | 0.999859 |
| Q4_0 | 324 KiB | 4.50 | 7.1x | 0.08590 | 0.996448 |
| Q4_1 | 360 KiB | 5.00 | 6.4x | 0.07818 | 0.997041 |
| Q5_0 | 396 KiB | 5.50 | 5.8x | 0.04270 | 0.999125 |
| Q8_0 | 612 KiB | 8.50 | 3.8x | 0.00535 | 0.999993 |
| Q2_K | 189 KiB | 2.62 | 12.2x | 0.28998 | 0.959120 |
| Q3_K | 247.5 KiB | 3.44 | 9.3x | 0.15085 | 0.988826 |
| Q4_K | 324 KiB | 4.50 | 7.1x | 0.07447 | 0.997288 |
| Q5_K | 396 KiB | 5.50 | 5.8x | 0.03693 | 0.999331 |
| Q6_K | 472.5 KiB | 6.56 | 4.9x | 0.01834 | 0.999835 |
| Q8_K | 657 KiB | 9.12 | 3.5x | 0.00695 | 0.999982 |

怎麼讀這張表：

- **Q4_0 與 Q4_K 大小完全一樣（324 KiB），但 Q4_K 的 RMSE 低 13%**（0.0745 vs 0.0859）。
  同樣的位元數，K-quant 就是比較準，代價是解量化程式碼複雜得多、CPU 上稍慢。
- **Q2_K 的餘弦相似度掉到 0.959。** 低於 0.99 就要小心了，這是「能跑但明顯變笨」的區間。
- **Q8_0 幾乎無損**（RMSE 0.0054），所以它是「保底選項」：當你不確定某個張量能不能壓，
  就留 Q8_0。

> **一個小陷阱**：F16 那一列的餘弦相似度是 1.000002，**大於 1**。
> 那不是量化出錯，是 f32 累加誤差（內積與兩個範數各自有捨入誤差）。
> 真要嚴格比較時，把內積與範數都轉 f64 再算，或直接把結果 clamp 到 1.0。

## 4. 離群值：量化的真正敵人

第一節說「區塊大小決定災情範圍」。這句話值得用數字證明。

實驗：把 768×768 矩陣的第 0 個元素從隨機值改成 **100.0**，然後分兩區量誤差。

```rust
// 只看前 32 個元素（離群值所在的那一個 Q4_0 區塊）。
let bad = rmse_of(&flat, &flat_back, 0, 32);
// 看其餘 589792 個「正常」權重有沒有被牽連。
let rest = rmse_of(&flat, &flat_back, 32, flat.len());
```

實測：

| 方案 | 離群區塊 RMSE | 其餘權重 RMSE |
|---|---|---|
| per-tensor 4bit（無區塊） | 0.8996 | **0.9992** |
| Q4_0（32 一組） | 0.8996 | 0.0859 |
| Q4_K（256 一組，8 子區塊） | 0.8040 | 0.0745 |
| Q8_0（32 一組，8 bit） | 0.2408 | 0.0054 |

這張表要讀出三件事，而且第三件跟直覺相反：

**第一，per-tensor 與 Q4_0 在離群值那一欄一模一樣（都是 0.8996）。**
不是巧合。離群值就在第 0 個位置，它的區塊縮放係數必然等於「全域最大絕對值 ÷ 7」，
兩種做法在那個區塊上是同一個算式。Q4_K 是 0.8040，好 11%，
但那是「從毀掉變成毀得輕一點」——別把這 11% 誤讀成「Q4_K 能扛離群值」。
**4-bit 救不了離群值本身。**

**第二，真正的傷害在「其餘權重」那一欄。**
per-tensor 是 0.9992——這個數字幾乎等於原始權重的標準差（我們造的是 N(0,1)）。
意思是：**正常權重全部被還原成 0**。步進 100/7 ≈ 14.3，比 99% 的權重都大，
四捨五入後全部歸零。這才是離群值最致命的地方：不是它自己失真，是它把其他 58 萬個權重一起抹平。

換成 Q4_0，其餘權重立刻從 0.9992 掉到 0.0859，差 11.6 倍。
這就是「區塊量化」的全部價值：把污染半徑從「整個張量」縮到「32 個權重」。
以 0.1B 的 `ffn.value`（3072×768 = 235 萬個權重）來說，受災比例是 0.0014%。

**第三，Q4_K 的優勢主要在「其餘權重」上**（0.0745 vs 0.0859，好 13%），
靠的是 8 個子區塊各自的 6-bit 縮放，讓正常權重那一側的解析度更細。
它在離群區塊上只贏 11%，兩者都還是 0.8 量級——而原始權重的標準差是 1，
意思是那個區塊基本上已經毀了。很多人把「Q4_K 品質比較好」誤解成「Q4_K 比較耐離群值」，其實不是。

那要怎麼處理離群值？只有一條路：**把它找出來，單獨給高精度**。
這就是下一節與第九節的主題。

## 5. QMatMul：為什麼推論時不 dequant

如果你每次前向都 `dequantize()` 再 `matmul()`，那量化只省了硬碟空間，沒省算力。
真正的做法是 `QMatMul`：

```rust
use candle_core::quantized::QMatMul;

// 把 QTensor 包成一個「可以 forward 的層」。注意它包的是 2D 矩陣。
let qmm = QMatMul::from_qtensor(qt)?;

// 前向：內部走的是量化 GEMM——直接把 4-bit 整數載入向量暫存器，
// 在暫存器裡乘加，不還原成 f32。
let y = qmm.forward(&x)?;
```

為什麼量化 GEMM 比較快？不是因為算得少，而是因為**記憶體頻寬**。
矩陣乘法是記憶體受限（memory-bound）的操作：每算一次乘加要讀一個權重。
Q4_K 把每個權重從 4 bytes 壓到 0.5625 bytes，等於同樣的頻寬能餵 7 倍的運算。
在 3050 這種頻寬只有 192 GB/s 的行動 GPU 上，這個差距比算力差距有感得多。

`QMatMul` 還有兩個你以後會用到的東西：

```rust
// 詞嵌入查表：量化後的 embedding 不能直接 index_select，
// 因為每個元素是半個位元組，索引不到「第 n 個權重」。
let e = qt.embedding(&ids)?;

// MoE 的 expert 路由：DeepSeek 那種架構會用到，見第九節。
let y = qt.indexed_moe_forward(&x, &expert_ids)?;
```

```text

大小：3.03 GiB

【中繼資料】共 24 筆
  general.architecture = String("rwkv7")
  general.file_type = U32(7)              ← 7 = Q8_0
  general.name = String("rwkv7-g1k-2.9b-20260930-ctx25600.pth")
  general.quantization_version = U32(2)
  rwkv7.attention.decay_lora_rank = U32(96)
  rwkv7.attention.gate_lora_rank = U32(320)
  rwkv7.attention.iclr_lora_rank = U32(96)

  rwkv7.block_count = U32(32)
  rwkv7.context_length = U32(1048576)
  rwkv7.embedding_length = U32(2560)
  rwkv7.feed_forward_length = U32(10240)
  rwkv7.wkv.head_size = U32(64)
  tokenizer.ggml.tokens = [陣列，65536 項]

【張量】共 902 個

  型別分佈：
    F16      192 個    150.31 MiB  (4.8%)
    F32      516 個     65.98 MiB  (2.1%)
    Q8_0     194 個      2.82 GiB  (93.0%)
```

四個值得停下來看的細節：

1. **902 個張量，只有 194 個被量化。** 其餘 708 個是 F16/F32——它們是 LayerNorm、
   `x_r/x_w/x_k` 這類 1 維或 3 維參數。量化這些不但省不下空間，還會增加解量化開銷。
2. **F32 有 516 個但只佔 66 MiB。** 對照 F16 的 192 個佔 150 MiB——平均每個 F32 張量比 F16 小，
   說明 F32 那批全是小張量（`w0`、`a0`、`v0`、`k_k` 這種 2560 維的向量）。
3. **`rwkv7.attention.gate_lora_rank = 320`**，但 0.1B 的 `g1` 只有 128 維。
   這個欄位不能從 hidden_size 推，必須從權重形狀讀——candle 的 `infer_lora_dims()` 就是幹這個的。
4. **`general.file_type = 7` 對應 Q8_0**，但檔案裡混了三種型別。
   這個欄位只是「主要型別」的標籤，載入器不會拿它來決定每個張量怎麼解。

### GGUF 的檔案佈局

```text
┌────────────────────────────────────┐
│ magic  "GGUF"            4 bytes   │
│ version  u32             4 bytes   │
│ n_tensors u64                      │
│ n_kv      u64                      │
├────────────────────────────────────┤
│ 中繼資料 kv 對（key, type, value）  │
├────────────────────────────────────┤
│ 張量資訊表（name, n_dims, dims,     │
│             dtype, offset）         │
├────────────────────────────────────┤
│ padding → 對齊到 32 bytes           │  ← 硬性要求
├────────────────────────────────────┤
│ 張量資料區（每個張量前後也對齊 32）  │
└────────────────────────────────────┘
```

**32 位元組對齊不是建議，是規格。** GPU 與 SIMD 都靠它做向量化載入，
不對齊會直接讀到錯的位元組。candle 的 `gguf_file::write` 內部有處理：

```rust
// 每一段資料後面補到 32 的倍數。
let padding = 31 - (31 + size_in_bytes) % 32;
```

## 7. 自己動手：402 個張量 → 一個 GGUF

`02_quantize_safetensors.rs` 的完整流程，五個步驟。

### 7.1 讀 safetensors

```rust
// 一次讀進記憶體。0.1B 是 382 MB，1.5B 是 3 GB，16 GB 都吃得下。
// 更大的模型就得改用 mmap 分批處理。
let tensors: HashMap<String, Tensor> = candle_core::safetensors::load(&args.src, &dev)?;

// 依名字排序，讓輸出可重現（HashMap 的迭代順序是隨機的）。
let mut names: Vec<&String> = tensors.keys().collect();
names.sort();
```

### 7.2 決定每個張量的型別

這是整個流程唯一需要判斷力的地方：

```rust
fn pick_dtype(name: &str, shape: &[usize], default: GgmlDType) -> GgmlDType {
    // 只看二維張量。一維（LayerNorm）與三維（x_r/x_w 之類）元素太少，
    // 量化省不下空間，反而增加解量化開銷。
    if shape.len() != 2 {
        return GgmlDType::F16;
    }
    // 最後一維必須能被區塊大小整除，否則量化函式直接報錯。
    let last = *shape.last().unwrap();

    // 詞嵌入與輸出頭特別敏感：embedding 是查表（誤差不會被平均掉），
    // head 直接決定 logits。這兩者一律給更高精度。
    let is_sensitive = name.contains("emb.weight") || name.contains("head.weight");
    if is_sensitive {
        // Q6_K 需要 256 的倍數；65536 與 768 都滿足。
        if last % 256 == 0 {
            return GgmlDType::Q6K;
        }
        // 退一步用 Q8_0（只需要 32 的倍數）。
        return GgmlDType::Q8_0;
    }

    // 一般張量：檢查能不能被目標型別的區塊大小整除。
    if last % default.block_size() != 0 {
        // 不能整除就退回 F16。Q4_K 的 256 很嚴格，
        // 所以 w1/g1 這類小矩陣（最後一維 64/128）在 Q4_K 下必然落到這裡。
        return GgmlDType::F16;
    }
    // 一切合格，用使用者指定的型別。
    default
}
```

### 7.3 量化

```rust
// QTensor::quantize 內部會先 to_dtype(F32) 再 flatten_all()，
// 所以 BF16 → 量化的過程不會有額外的精度損失。
let qt = QTensor::quantize(t, dtype)?;
// 累計統計，最後印型別分佈。
stats.entry(format!("{dtype:?}")).or_insert((0, 0)).1 += qt.storage_size_in_bytes();
```

### 7.4 組中繼資料

這些 key 不是查文件抄的，是從你那份 2.9B GGUF 的 header 一個一個對出來的：

```rust
let meta: Vec<(String, Value)> = vec![
    // 架構名稱，llama.cpp 靠它選載入器。
    ("general.architecture".into(), Value::String("rwkv7".into())),
    // 檔案類型標記，固定 model。

    ("rwkv7.wkv.head_size".into(), Value::U64(64)),

    ("rwkv7.attention.decay_lora_rank".into(), Value::U64(64)),
    ("rwkv7.attention.iclr_lora_rank".into(), Value::U64(64)),
    ("rwkv7.attention.value_residual_mix_lora_rank".into(), Value::U64(32)),
```

### 7.5 寫檔


### 7.6 實測結果

```text
$ 02_quantize_safetensors --dtype q8_0
讀入 402 個張量，耗時 1.2s
型別分佈：
  F16     220 個張量    330.00 KiB
  Q6K       2 個張量     78.75 MiB
  Q8_0    180 個張量     91.45 MiB
原始   364.50 MiB
輸出   170.55 MiB
壓縮比 2.14x
總耗時 5.2s

$ 02_quantize_safetensors --dtype q4k
  F16     280 個張量      5.40 MiB
  Q4K     120 個張量     46.99 MiB
  Q6K       2 個張量     78.75 MiB
原始   364.50 MiB
輸出   131.16 MiB
壓縮比 2.78x
總耗時 7.0s
```

**這裡有個讓人失望但很重要的事實：Q4_K 只有 2.78x，不是理論上的 7x。**

拆開來看（`03_inspect_gguf` 對自製 Q4_K 檔案的區塊統計）：

```text
  型別分佈：
    F16      280 個      5.40 MiB  (4.1%)
    Q4K      120 個     46.99 MiB  (35.8%)
    Q6K        2 個     78.75 MiB  (60.1%)

  區塊分佈：
    blocks          52.39 MiB  (39.9%)
    emb             39.38 MiB  (30.0%)
    head            39.38 MiB  (30.0%)
```

兩個原因：

1. **emb + head 佔了 60.1%。** 它們被刻意留在 Q6_K，因為這兩個張量最敏感。
   你把它們也壓到 Q4_K，檔案會變成 ~90 MiB（3.9x），但模型會明顯變笨。
2. **Q4_K 對小矩陣不友善。** `w1` 是 [768, 64]、`g1` 是 [768, 128]，
   最後一維不是 256 的倍數，只能留 F16。12 層 × 4 個這種張量，白送 5.4 MiB。
   注意 Q8_0 版本只有 220 個 F16（330 KiB），因為 32 的倍數寬鬆得多。

**這就是為什麼 llama.cpp 的 Q4_K_M 是「混合」而不是「全部 Q4_K」**：
大矩陣壓 4 bit，小矩陣與敏感張量留高精度。你剛才手寫的 `pick_dtype` 就是這個邏輯的簡化版。

## 8. 三個坑

### 坑一：形狀 ≠ 佈局，K-quant 只認最後一維

`QTensor::quantize` 會把張量攤平再切區塊，所以「768×64 攤平後 49152 能被 256 整除」
在數學上是成立的——但這會產生一個 **llama.cpp 讀不動的 GGUF**。

llama.cpp 的 K-quant 解量化 kernel 假設「每一列是獨立的區塊序列」，
所以硬性要求 `最後一維 % 256 == 0`。candle 不管這件事，因為它自己的 kernel 就是攤平處理的。

**結論**：`pick_dtype` 裡那句 `if last % default.block_size() != 0 { return F16 }` 不是保險，
是必要的正確性檢查。

### 坑二：張量名稱是方言，不是標準

這是本章最重要的一個發現。你那份 2.9B GGUF 裡的張量叫 `blk.0.time_mix_value.weight`；
你的 safetensors 裡同一個權重叫 `blocks.0.att.value.weight`。對照表：

| candle safetensors | llama.cpp GGUF |
|---|---|
| `emb.weight` | `token_embd.weight` |
| `head.weight` | `output.weight` |
| `blocks.N.ln0` | `token_embd_norm` |
| `blocks.N.ln1` | `blk.N.attn_norm` |
| `blocks.N.ln2` | `blk.N.attn_norm_2` |
| `blocks.N.att.receptance.weight` | `blk.N.time_mix_receptance.weight` |
| `blocks.N.att.key.weight` | `blk.N.time_mix_key.weight` |
| `blocks.N.att.value.weight` | `blk.N.time_mix_value.weight` |
| `blocks.N.att.output.weight` | `blk.N.time_mix_output.weight` |
| `blocks.N.att.ln_x` | `blk.N.time_mix_ln` |
| `blocks.N.att.x_r/x_w/x_k/x_v/x_a/x_g` | `blk.N.time_mix_lerp_fused`（六個融成一個） |
| `blocks.N.att.w0/w1/w2` | `blk.N.time_mix_w0/w1/w2` |
| `blocks.N.att.a0/a1/a2` | `blk.N.time_mix_a0/a1/a2` |
| `blocks.N.att.v0/v1/v2` | `blk.N.time_mix_v0/v1/v2` |
| `blocks.N.ffn.key.weight` | `blk.N.channel_mix_key.weight` |
| `blocks.N.ffn.value.weight` | `blk.N.channel_mix_value.weight` |
| `blocks.N.ffn.x_k` | `blk.N.channel_mix_lerp_k` |
| `ln_out` | `output_norm` |

兩個後果：

1. **你那份 2.9B Q8_0 丟給 candle 的 `VarBuilder::from_gguf` 會失敗**，
   因為它會去找 `blocks.0.att.receptance.weight`。必須先寫一層名稱映射。
2. **用本文產出的 GGUF 丟給 llama.cpp 也讀不動**，除了名字不對，還缺詞表。

那個「六個 `x_*` 融成一個 `time_mix_lerp_fused`」的設計值得注意：
llama.cpp 把六個 `[1,1,c]` 的向量拼成一個 `[c,1,1,6]` 張量，
一次載入、一次算完，減少六次 kernel launch。這是推論引擎為了速度做的重排，
代價就是「權重檔案不能互換」。

### 坑三：缺詞表

candle 的 `quantized_var_builder::from_gguf` 只讀張量，不讀詞表，
所以本文產出的 GGUF 給 candle 用完全沒問題。但 llama.cpp 需要：

```text
tokenizer.ggml.model      = "rwkv"
tokenizer.ggml.tokens     = [65536 個字串]
tokenizer.ggml.token_type = [65536 個 i32]
tokenizer.ggml.bos_token_id = 0
tokenizer.ggml.eos_token_id = 0
tokenizer.ggml.eot_token_id = 261
tokenizer.chat_template   = "..."
```

`tokenizer.ggml.tokens` 從你模型目錄下的 `rwkv_vocab_v20230424.json` 讀出來填進去就好，
但那會讓檔案多約 1.5 MB，而且寫 65536 個字串會讓 `gguf_file::write` 慢上幾秒。
本章刻意不做——因為**教學重點在張量，不在詞表**，而且 candle 根本不需要它。

## 9. 與 DeepSeek、Qwen 的連線

量化這件事，各家模型的難點完全不同。把上面學到的東西接到你熟悉的大陸模型上：

### Qwen 的 GQA：為什麼量化收益跟 Llama 不一樣

Qwen2.5 / Qwen3 用 GQA（grouped-query attention），KV 頭數遠少於 Q 頭數。
結果是：**KV 投影矩陣比 Llama 小，FFN 佔的比例更大**。
所以 Qwen 系列量化後，`ffn` 那幾個張量是主要受益者，而 attention 部分省不下多少。

對照 RWKV-7：它根本沒有 KV cache，`att` 只有 receptance / key / value / output 四個
`[c, c]` 矩陣，其餘全是低秩分解（`w1/w2` 是 `[c,64]` 與 `[64,c]`）。
所以 RWKV-7 的量化收益幾乎全在 **emb + head + ffn** 上——這正是第七節量到的 60.1%。

### DeepSeek 的 MoE：量化難點在「每個 expert 都很小」

DeepSeek-V2/V3 是 MoE，一個 671B 的模型裡有 256 個 routed expert，每個只有約 2B。
量化時會遇到兩個新問題：

1. **expert 之間的權重分佈差異很大。** 用同一個 scale 處理所有 expert 會讓某些 expert 失真。
   實務做法是 per-expert 量化，也就是回到本文第四節的結論：**限制污染半徑**。
2. **路由權重不能量化。** gate 的輸出決定選哪個 expert，一點誤差就會讓整個 token 走錯路。
   所以 gate 一律留 F32——這跟你那份 2.9B GGUF 把 `time_mix_lerp_fused` 留 F32 是同一個邏輯。

candle 對這件事有專門的 API：

```rust
// 每個 token 走不同的 expert，所以不能整體 matmul。
// indexed_moe_forward 接受 expert id 清單，內部做 gather + 分組 GEMM。
let y = qt.indexed_moe_forward(&x, &expert_ids)?;
```

### imatrix：把位元花在刀口上

llama.cpp 的 `--imatrix` 是這個思路的極致：先跑一批校準資料，
統計每個「輸入通道」對輸出的重要程度，然後在量化時給重要通道更高權重。

candle 直接支援：

```rust
// imatrix_weights 的長度必須等於張量的最後一維（每個輸入通道一個權重）。
// 內部會用這些權重去調整每個區塊的縮放係數。
let qt = QTensor::quantize_imatrix(&t, &imatrix_weights, GgmlDType::Q4K)?;
```

`imatrix_file::load_imatrix(path)` 可以直接讀 llama.cpp 產生的 `.imatrix` 檔。
如果你哪天想把自己微調過的模型壓到 Q4_K 又不想掉太多品質，這是標準做法。
