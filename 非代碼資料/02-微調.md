## 0. 先算顯存：6 GB 能動什麼

微調的顯存不是「參數量 × 4」這麼簡單。一個參數在訓練時會佔好幾份：

| 項目 | 大小（0.1B） | 說明 |
|---|---|---|
| 主權重（F32） | 764 MB | 191M × 4 bytes |
| 梯度 | 764 MB | 與參數同形狀 |
| AdamW 一階動量 | 764 MB | 與參數同形狀 |
| AdamW 二階動量 | 764 MB | 與參數同形狀 |
| BF16 原始張量 | 382 MB | 轉 F32 之後其實可以丟，但作用域還沒結束 |
| `f32_tensors` 那份 | 764 MB | `Var::from_tensor` 會複製，原件還活著 |
| emb / head 重複 | ~600 MB | `head.weight` 與 `head_t`（預轉置）各一份 |
| 配置器碎片 | ~900 MB | candle 的 CUDA 配置器不把塊還給驅動 |
| **固定成本小計** | **約 5.7 GB** | 這部分與 chunk 無關 |
| 活化值 | 每 token 約 25 MB | **隨 chunk 線性成長**（反向要留中間結果） |
| **實測峰值（chunk=8）** | **5926 MiB** | `nvidia-smi` 採樣，6 GB 卡的極限 |

> 這張表是**實測校準過的**，不是紙上估算。我第一版寫「約 3.6 GB、chunk 對顯存幾乎沒影響」，
> 兩個數字都錯：真實固定成本是 5.7 GB，而且活化值確實隨 chunk 成長，
> chunk=9 就 OOM。完整數據見第 6.2 節。

四個由此推出的結論：

1. **0.1B 可以做全量微調**，但 chunk 上限只有 8，而且不能同時開 Chrome。
2. **1.5B 不可能全量**：固定成本是 0.1B 的 7.9 倍，約 45 GB。
   要動 1.5B 只有兩條路：LoRA（凍結主體，只訓練 0.5% 的參數），或者把主體留在 BF16
   （3.05 GB）並用 `bf16` 混合精度——但 candle 的 AdamW 只支援 f32 主權重，這條路走不通。
3. **chunk 對顯存的影響不是「極小」，而是「很致命」**。
   推論時 RWKV 的 `State` 確實是固定大小（這是它相對 Transformer 的真優勢），
   但**訓練時每個 token 的前向都會在計算圖上留節點**，反向要沿著鏈回傳，
   所以活化值一樣隨 chunk 線性成長。你省下的只有 attention 的 KV，不是整個計算圖。
4. **優化器狀態（1.5 GB）比參數本身還大。** 想省顯存，先動優化器（換 SGD 省 1.5 GB），
   再動那些重複的副本（省 1.7 GB），而不是縮 chunk。

## 1. candle 的自動微分模型

candle 沒有 `requires_grad` 旗標，它用型別來區分：

| 型別 | 角色 | 有沒有梯度 |
|---|---|---|
| `Tensor` | 一般的多維陣列 | 只有當它是某個 `Var` 的後代時才有 |
| `Var` | 可訓練參數，包著一個 `Tensor` 並標記 `is_variable = true` | 有 |
| `VarMap` | `HashMap<String, Var>`，參數倉庫 | — |
| `GradStore` | `loss.backward()` 的回傳值，張量 id → 梯度 | — |

關鍵是這條鏈：`Var` →（各種運算）→ `Tensor`（logits）→ loss → `backward()` → `GradStore`。
中間任何一步用了「不記錄運算」的函式（例如 `.to_vec1()`、`.detach()`），鏈就斷了。

三個必記的 API：

```rust
// 1. 從張量造一個可訓練參數。會複製 storage 並標記 is_variable。
let v = Var::from_tensor(&tensor)?;

// 2. 前向之後拿到梯度。GradStore 用「張量 id」查，不是用名字。
let grads = loss.backward()?;

// 3. 查某個參數的梯度。注意要傳 as_tensor()，因為 store 的 key 是 Tensor。
if let Some(g) = grads.get(v.as_tensor()) {
    // g 的形狀與 v 相同。
}
```

`Optimizer` trait 只有五個方法，全部要自己接：

```rust
pub trait Optimizer: Sized {
    type Config: Sized;
    fn new(vars: Vec<Var>, config: Self::Config) -> Result<Self>;
    fn step(&mut self, grads: &candle::backprop::GradStore) -> Result<()>;
    fn learning_rate(&self) -> f64;
    fn set_learning_rate(&mut self, lr: f64);
    // 這個有預設實作，等於 backward + step 兩步。
    fn backward_step(&mut self, loss: &Tensor) -> Result<()> { /* ... */ }
}
```

## 2. 第一個坑：`VarMap::set` 不會新增

直覺寫法是把 safetensors 讀出來，`varmap.set(...)` 塞進去。跑起來會得到：

```text
Error: cannot find blocks.0.ffn.key.weight in VarMap
```

看原始碼就懂了：

```rust
// candle-nn/src/var_map.rs
pub fn set<I: Iterator<Item = (K, V)>, K: AsRef<str>, V: AsRef<Tensor>>(
    &mut self, iter: I,
) -> Result<()> {
    let tensor_data = self.data.lock().unwrap();
    for (name, value) in iter {
        match tensor_data.get(name) {
            // 只更新，不存在就直接報錯。
            None => candle::bail!("cannot find {name} in VarMap"),
            Some(var) => { var.set(value.as_ref())?; }
        }
    }
    Ok(())
}
```

`set` 的語意是「**更新已存在的變數**」，不是「插入」。第一次填充必須直接操作底層 HashMap：

```rust
// varmap.data() 回傳 &Mutex<HashMap<String, Var>>，是公開 API。
{
    // 作用域寫窄，離開 block 就釋放鎖，避免後面死鎖。
    let mut data = varmap.data().lock().unwrap();
    for (name, tensor) in &f32_tensors {
        // Var::from_tensor 會複製一份 storage 並標記為可訓練，
        // 所以原本的 f32_tensors 可以安全丟掉。
        data.insert(name.clone(), Var::from_tensor(tensor)?);
    }
}
```

> **為什麼要轉 F32？** safetensors 是 BF16，但 AdamW 的動量緩衝若用 BF16 會嚴重掉精度。
> 業界慣例是「BF16 前向 + F32 主權重」，candle 只有後者，所以載入時就轉 F32。
> 0.1B 轉完是 764 MB，吃得下；1.5B 轉完是 6.1 GB，這就是為什麼 1.5B 只能走 LoRA。

## 3. 第二個坑：`get_unchecked` 不支援 VarMap

填好 VarMap、建好 VarBuilder，`Model::new` 卻報：

```text
Error: 模型建構失敗：形狀與權重不符
Caused by: `get_unchecked` does not make sense for `VarMap`, use `get`.
```

原因在 `rwkv_v7.rs` 的這段：

```rust
// candle-transformers/src/models/rwkv_v7.rs
fn infer_lora_dims(vb: &VarBuilder) -> Result<(usize, usize, usize, usize)> {
    let att = vb.pp("blocks").pp(0).pp("att");
    // get_unchecked 只給名字、不給形狀，用來「先探一下維度再決定怎麼建」。
    let d_decay = att.get_unchecked("w1")?.dim(1)?;
    let d_aaa = att.get_unchecked("a1")?.dim(1)?;
    let d_mv = att.get_unchecked("v1")?.dim(1)?;
    let d_gate = att.get_unchecked("g1")?.dim(1)?;
    Ok((d_decay, d_aaa, d_mv, d_gate))
}
```

`get_unchecked` 只實作在 safetensors/mmap 這類後端上，`VarMap` 沒有。
**結論：`VarBuilder::from_varmap` 根本建不出 `rwkv_v7` 模型。**

兩條解法：

**A. fork 模型檔案**，把 4 處 `get_unchecked` 改成 `get`。
   缺點是跟著上游升級會痛，而且 `get` 需要形狀，得先知道 `w1` 是 `[768, 64]`。

**B. 自己包一層 backend。** `SimpleBackend` 是公開 trait：

```rust
pub trait SimpleBackend: Send + Sync {
    fn get(&self, s: Shape, name: &str, h: Init, dtype: DType, dev: &Device) -> Result<Tensor>;
    fn get_unchecked(&self, name: &str, dtype: DType, dev: &Device) -> Result<Tensor>;
    fn contains_tensor(&self, name: &str) -> bool;
}
```

只要 30 行就能把 `VarMap` 包成「會轉接 `get_unchecked`」的版本：

```rust
struct VarmapBackend {
    // 真正的參數倉庫。
    map: VarMap,
}

impl SimpleBackend for VarmapBackend {
    // 有給形狀的一般取用：直接轉給 VarMap，它會檢查形狀是否相符。
    fn get(
        &self, s: Shape, name: &str, h: Init, dtype: DType, dev: &Device,
    ) -> CandleResult<Tensor> {
        self.map.get(s, name, h, dtype, dev)
    }

    // 只給名字的取用：VarMap 沒實作，我們自己查表。
    // 因為權重是從 safetensors 原樣載入的，形狀一定正確，不需要再檢查。
    fn get_unchecked(&self, name: &str, _dtype: DType, _dev: &Device) -> CandleResult<Tensor> {
        // 取鎖查表。
        let data = self.map.data().lock().unwrap();
        match data.get(name) {
            // as_tensor() 回傳 Var 內部的張量視圖，帶梯度追蹤。
            Some(var) => Ok(var.as_tensor().clone()),
            // 找不到就明確報錯，訊息帶上名字，比 upstream 的通用錯誤好查。
            None => candle_core::bail!("VarmapBackend: 找不到參數 {name}"),
        }
    }

    // 模型載入時用這個判斷「某個可選張量存不存在」（例如 v7a 的 s_emb_x）。
    fn contains_tensor(&self, name: &str) -> bool {
        self.map.data().lock().unwrap().contains_key(name)
    }
}
```

用法：

```rust
// 注意是 from_backend 而不是 from_varmap。
let vb = VarBuilder::from_backend(
    // clone 是 Arc 級別的複製，共用同一份參數。
    Box::new(VarmapBackend { map: varmap.clone() }),
    // 主權重用 F32。
    DType::F32,
    // 裝置。
    dev.clone(),
);
```

> 這是 candle 唯一留給使用者的縫。`VarBuilder` 本身是 enum 不是 trait，改不了；
> 但 `SimpleBackend` 是 trait，`from_backend` 是公開 API。
> 記住這個技巧——文件三要用它來做「量化主體 + fp32 旁路」。

## 4. 第三個坑：沒有 `clip_grad_norm`

candle 沒有內建梯度裁剪。自己寫一次就懂 PyTorch 那個函式在做什麼：

```rust
fn clip_grad_norm(grads: &mut GradStore, vars: &[Var], max_norm: f32) -> Result<f32> {
    // 先把所有梯度平方和累加起來。
    let mut sum_sq = 0f32;
    for v in vars {
        // 沒有梯度代表這個參數沒參與計算（例如被凍結）。
        if let Some(g) = grads.get(v.as_tensor()) {
            // 平方後全部加總，轉成純量。
            sum_sq += g.sqr()?.sum_all()?.to_scalar::<f32>()?;
        }
    }
    // 開根號得到 L2 範數。
    let norm = sum_sq.sqrt();

    // 超過上限才縮放，沒超過就原樣放行（這是 clip 而不是 normalize）。
    if norm > max_norm {
        // 加 1e-6 是為了避免除以零。
        let scale = (max_norm / (norm + 1e-6)) as f64;
        for v in vars {
            if let Some(g) = grads.get(v.as_tensor()) {
                // 必須用 insert 覆寫，因為 Optimizer::step 讀的是 store 裡的值。
                grads.insert(v.as_tensor(), (g * scale)?);
            }
        }
    }
    Ok(norm)
}
```

**這裡有個反直覺的實測結果。** 這個模型在 `chunk=8` 時的梯度範數是 **600~1000** 量級：

```text
step   1  loss 7.3660  |g| 666.521
step   2  loss 6.7946  |g| 996.713
step   3  loss 7.2443  |g| 1010.359
```

不是 bug。詞表 65536，softmax 的梯度會在 6.5 萬維上累加，範數自然大。

**所以 `clip` 千萬別設 1.0**——那等於把學習率再除以 700，
loss 會看起來完全不會動，然後你會花兩小時以為自己的訓練迴圈寫錯了。
本範例預設 10.0，是「該剪的時候剪、不該剪的時候放行」的折衷。

## 5. 訓練迴圈：RWKV 為什麼只能逐 token

Transformer 訓練可以一次算完整個序列（teacher forcing，平行）。
RWKV 不行——`candle-transformers` 的 `rwkv_v7` 只提供兩個前向：

```rust
// 單 token 前向，RNN 風格。要自己維護 state。
pub fn forward(&self, xs: &Tensor, state: &mut State, token_ids: &[u32]) -> Result<Tensor>;

// 整個序列一次算完，但只回傳「最後一個 token」的 logits。
// 用來做 prompt 預處理很快，但訓練時拿不到中間位置的 logits。
pub fn forward_seq(&self, token_ids: &[u32], state: &mut State) -> Result<Tensor>;
```

`forward_seq` 只回最後一個 logits，所以訓練必須逐 token 呼叫 `forward`：

```rust
// 每個 chunk 都重建狀態。這一步等同於 PyTorch 的 state.detach()，
// 但 candle 的 State 沒有 detach 方法，直接重建最乾淨。
let mut state = State::new(&cfg, &dev)?;

// 收集每個位置的 logits。
let mut logits_per_pos: Vec<Tensor> = Vec::with_capacity(args.chunk);
for tok in input {
    // 輸入張量形狀必須是 (batch=1, seq=1)，因為 Model::forward 內部會 squeeze 兩次。
    let xs = Tensor::from_vec(vec![*tok], (1, 1), &dev)?;
    // 前向一個 token。第三個參數是 token id 切片，v7a/v7b 的 DeepEmbed 會用到。
    let logits = model.forward(&xs, &mut state, &[*tok])?;
    // 形狀是 (vocab_size,)，收起來。
    logits_per_pos.push(logits);
}

// 把 chunk 個 (vocab,) 疊成 (chunk, vocab)。
let logits = Tensor::stack(&logits_per_pos, 0)?;
```

這就是 **TBPTT（Truncated Backpropagation Through Time）**：
每個 chunk 從乾淨狀態開始，梯度不跨 chunk 累積，記憶體才不會無限成長。

代價與取捨（下表是**實測**，不是估算，數字來源見 6.1 節）：

| chunk | 每步耗時（GPU） | 每 token | 顯存 | 梯度品質 |
|---|---|---|---|---|
| 2 | 2.9s | 1.45s | 5926 MiB | 只看 2 個 token，雜訊極大 |
| 4 | 6.3s | 1.58s | 5926 MiB | 雜訊大 |
| 8 | 9.2s | 1.15s | 5926 MiB | 勉強可用，**6 GB 上的硬上限** |
| 9 | — | — | **OOM** | 多一個 token 就爆 |
| 16 / 32 / 64 | — | — | **OOM** | 跑不動 |

> **這裡要修正一個常見誤解**（包含我自己第一版的寫法）：
> 「RWKV 的 state 是固定大小，所以 chunk 再大顯存也不變」——這句話**只對推論成立**。
>
> 訓練時每個 token 的前向都會在計算圖上留節點，`loss.backward()` 要沿著這條鏈回傳梯度，
> 所以**活化值是隨 chunk 線性成長的**，跟 Transformer 沒有本質差別。
> 你唯一省下的是 attention 的 KV（RWKV 用固定大小的 state 取代），
> 而不是整個計算圖。
>
> 在 6 GB 的 3050 上，這個線性成長的斜率大到 chunk=12 就撞牆——
> 因為固定成本（參數＋梯度＋AdamW）已經吃掉 5.7 GB，活化值只剩約 200 MB 的餘地。

## 6. 實測：0.1B 全量微調

完整流程（`04_train_full.rs` 的骨架）：

```rust
// 1. 讀 safetensors（BF16）。
let raw = candle_core::safetensors::load(small_01b(), &dev)?;

// 2. 轉 F32 並放進 VarMap。
let f32_tensors: Vec<(String, Tensor)> = raw.iter()
    // to_dtype 會產生新張量。
    .map(|(k, v)| Ok((k.clone(), v.to_dtype(DType::F32)?)))
    .collect::<Result<Vec<_>>>()?;
// ……（填充 VarMap 見第 2 節）

// 3. 建模型。設定值全部來自 safetensors 的實際形狀，不是猜的。
let cfg = Config {
    // g1d 是純 v7，沒有 DeepEmbed（v7a）也沒有 DEA（v7b）。
    version: ModelVersion::V7,
    // 詞表大小，RWKV World 固定 65536。
    vocab_size: 65536,
    // 隱藏維度。
    hidden_size: 768,
    // 層數。
    num_hidden_layers: 12,
    // 每頭維度，G1 全系列都是 64。
    head_size: 64,
    // None 代表用 hidden × 4 = 3072，正好符合 ffn.key 的 [3072, 768]。
    intermediate_size: None,
    // 0 代表關閉「每 N 層縮放」，G1 世代不需要。
    rescale_every: 0,
};

// 4. 優化器。
let params = ParamsAdamW {
    // 全量微調用 1e-4 這種量級，比從零訓練小一到兩個數量級。
    lr: args.lr,
    beta1: 0.9,
    beta2: 0.999,
    eps: 1e-8,
    // LLM 微調的常見值。
    weight_decay: 0.01,
};
let mut opt = AdamW::new(vars.clone(), params)?;

// 5. 一個 step。
let loss = loss::cross_entropy(&logits, &target_t)?;
let mut grads = loss.backward()?;
let gnorm = clip_grad_norm(&mut grads, &vars, args.clip)?;
opt.step(&grads)?;
```

**語料怎麼來？** 這裡有個實用技巧。RWKV World 詞表的前 256 個詞元就是原始位元組
（token 1 = `0x00`、token 2 = `0x01`……），所以：

```rust
// byte + 1 就是合法的 token id。
// 這是 candle 的 rwkv_v7::Tokenizer 沒有 encode 方法時的標準替代方案。
fn encode_bytes(text: &str) -> Vec<u32> {
    text.as_bytes().iter().map(|b| *b as u32 + 1).collect()
}
```

代價是中文變成 3 bytes/字，32 個 token 只涵蓋約 10 個漢字。
好處是你不用自己實作那個貪婪分詞器，而且**這條路對任何 GGUF 都通用**。

**CPU 實測（chunk=8，僅供驗證邏輯，速度沒有參考價值）**：


如果 GPU 版跟 CPU 版差很多，那才是哪裡寫錯了。

**第二件事：加速比會隨 chunk 變大而崩掉。** 這是本章最值得看的一張表：

| chunk | CPU 每步 | GPU 每步 | 加速比 |
|---|---|---|---|
| 1 | 14.2s | 1.15s | **12.3×** |
| 2 | 14.7s | 2.9s | 5.1× |
| 4 | 16.6s | 6.3s | 2.6× |
| 8 | 17.2s | 9.2s | 1.9× |
| 32 | 406s | **OOM** | — |

看出來了嗎：**chunk 越小，GPU 贏得越多；chunk 越大，GPU 的優勢越薄。**
這跟直覺相反（通常大家以為「GPU 要餵大 batch 才有效率」），但把兩邊拆成
「固定成本 + 每 token 成本」就一目了然：

| | 固定成本／步 | 每 token 成本 |
|---|---|---|
| CPU | ~13.1s | ~0.4s |
| GPU | ~0.05s | ~1.1s |

驗算：GPU chunk=8 → 0.05 + 8×1.1 = 8.9s（實測 9.2s ✓）；
CPU chunk=8 → 13.1 + 8×0.4 = 16.3s（實測 17.2s ✓）。

**兩個反直覺的事實：**

1. **CPU 每步有 13 秒的固定成本。** 那不是前向，是 `opt.step(&grads)`——
   402 個張量、1.9 億個 f32 元素，每個都要算 `m = β₁m + (1−β₁)g`、
   `v = β₂v + (1−β₂)g²`、`θ −= lr·m̂/(√v̂+ε)`，再逐個寫回。
   candle 的 CPU 後端是單執行緒逐算子跑，這一步就吃掉 13 秒。
   **GPU 把這 13 秒壓到幾乎為零**，這才是那 12 倍加速的真正來源。
2. **GPU 的每 token 成本是 CPU 的 2.75 倍。** 對，你沒看錯——
   batch=1、hidden=768 這種規模，一次 linear 只有 2.4 MFLOP，
   3050 的 kernel 啟動開銷（約數十微秒 × 近千個算子）遠超過實際計算時間。
   CPU 反而沒有這個包袱：它的算子派發是函式呼叫，不是驅動呼叫。

所以整件事的真相是：**GPU 贏在優化器，輸在逐 token 計算。**
chunk 越大，後者佔的比重越高，加速比就越難看。

再往下追一層，為什麼逐 token 計算會這麼慢？三個原因疊加：

1. **RWKV 的時間維度無法平行。** `forward_seq` 原始碼裡就是 `for t in 0..seq_len`，
   一個 token 接一個 token 算。所以「chunk=8」等於「8 次完整前向」，
   不是 Transformer 那種「一次矩陣乘算完 8 個位置」。
2. **每次前向的張量都太小。** batch=1 讓每個矩陣乘都退化成「向量 × 矩陣」，
   GPU 的 2048 個 CUDA core 有 99% 在發呆。
3. **每個 token 有近千個小算子。** 一層 RWKV-7 block 有 time_mix（w0/w1/w2、
   a0/a1/a2、v0/v1/v2、g1/g2、r_k、k_k）、四個投影、ln_x、channel_mix，
   約 60~80 個張量運算；12 層就是 900 個左右，加上反向約 2700 個。

換句話說：**candle 的 RWKV 訓練在 batch=1 時是 host-bound，不是 device-bound。**

> **CPU chunk=32 為什麼是 406 秒？** 照上面的模型應該只要 26 秒。
> 實際差 15 倍，原因是這台只有 16 GB 記憶體：32 個 token 的計算圖
> 加上 5.7 GB 的參數／梯度／優化器狀態，把系統推進換頁（swap），
> 之後每一步都在跟硬碟打交道。**這也順便說明：CPU 路線不是「慢一點」，
> 是「超過某個 chunk 就直接崩」。** 我只跑了 1 步就停手，沒有繼續測。

### 6.2 顯存：6 GB 的天花板在哪

`nvidia-smi` 每 200 ms 採樣一次的結果：

| chunk | 峰值顯存 | 結果 |
|---|---|---|
| 1 | 5926 MiB | 成功 |
| 2 | 5926 MiB | 成功 |
| 4 | 5926 MiB | 成功 |
| 8 | 5926 MiB | 成功 |
| **9** | 5926 MiB | **OOM** ← 多一個 token 就爆 |
| 10 / 12 / 16 / 32 / 64 | 5926 MiB | **OOM** |

**這面牆是陡崖，不是斜坡。** chunk=8 跑得完 12 步，chunk=9 連第一步都進不去。
而且所有讀數都是同一個 5926 MiB——包含成功的那三次。

這件事的意義：**OOM 不是「活化值慢慢長大、終於超標」，而是「配置器湊不出下一個塊」。**
candle 的 CUDA 配置器在釋放張量後只把塊留在自己的池子裡，不還給驅動；
記憶體越滿，能湊出的連續塊越少。空閒時這張卡只被佔用 7 MiB，
所以 6144 − 5926 ≈ 218 MiB 是名目上的餘量，
但只要有一個稍大的配置請求（反向傳播要新建梯度張量，emb 的梯度是 65536×768×4 ≈ 201 MB）
就湊不出來，直接 OOM。

**這也解釋了為什麼縮小 chunk 到 2 並沒有省下多少**——省下的活化值
被配置器的碎片吃掉，讀數照樣是 5926。真正該動的是固定成本（見下面的槓桿）。

固定成本 5.7 GB 花在哪，逐項拆給你看（191 M 參數）：

| 項目 | 大小 | 說明 |
|---|---|---|
| F32 參數 | 764 MB | 402 個張量，從 BF16 轉上來 |
| F32 梯度 | 764 MB | `GradStore` 裡每個 Var 一份 |
| AdamW 的 m | 764 MB | 一階動量 |
| AdamW 的 v | 764 MB | 二階動量 |
| BF16 原始張量 | 382 MB | 轉完之後其實可以丟，但作用域還沒結束 |
| `f32_tensors` 那份 | 764 MB | `Var::from_tensor` 會複製，原件還活著 |
| emb / head 的重複 | ~600 MB | `head.weight` 與 `head_t`（預轉置）各一份 |
| 小計 | **~4.8 GB** | |
| 配置器碎片與暫存 | ~0.9 GB | candle 的 CUDA 配置器不會把釋放的塊還給驅動 |

**注意 AdamW 佔了 1.5 GB，比參數本身還多。** 這就是為什麼「縮小 chunk」救不了——
chunk 影響的是最後那 218 MiB，而前面 5.7 GB 是死的。

四條真正能動的槓桿，按性價比排序：

```rust
// 槓桿 1（省 1.5 GB，最划算）：換 SGD。
// 代價是收斂變慢、對學習率敏感，但 0.1B 這種小模型微調完全夠用。
let params = ParamsSGD { lr: args.lr, momentum: None, dampening: None, weight_decay: 0.0, ..Default::default() };

// 槓桿 2（省 764 MB）：填完 VarMap 立刻把中間那份丟掉。
// 現在 f32_tensors 一直活到函式結束，白佔 764 MB。
{
    let mut data = varmap.data().lock().unwrap();
    for (name, tensor) in f32_tensors.drain(..) {
        data.insert(name, Var::from_tensor(&tensor)?);
    }
}   // ← 這裡 drop，記憶體還給配置器

// 槓桿 3（省 ~400 MB）：不要同時留 head.weight 和 head_t。
// rwkv_v7 內部已經預轉置了一份，VarMap 裡那份只為了存檔而存在。

// 槓桿 4（省到幾乎為零）：LoRA。只有 adapter 進優化器，m/v 只有幾 MB。
// 這是唯一能讓 chunk 開到 512 的路，細節見第 7 節。
```

四條全上，固定成本可以壓到 1.5 GB 左右，活化值預算從 218 MiB 變成 4.5 GB，
chunk 開到 256 都不是問題。**但每 token 1.1 秒的 host 端成本不會因此改善**——
那要靠批次化（一次餵多條序列）或改寫模型，不是調參數能解的。

> 這也解釋了為什麼 1.5B 與 2.9B 在這台機器上不用想：
> 1.5B 的固定成本是 0.1B 的 7.9 倍，約 45 GB；
> 2.9B 是 15 倍，約 86 GB。這是算術，不是優化問題。

### 6.3 所以 GPU 到底該不該用

先給結論：**在這台機器上、batch=1 的 RWKV 訓練，GPU 值得用，但別期待十倍。**
chunk=8 時 CPU 17.2 秒、GPU 9.2 秒，實實在在快了 1.9 倍；
十步從 172 秒變 92 秒，一小時能多跑一倍實驗。這樣就夠了。

但如果你的期待是「插上顯卡就起飛」，那要理解為什麼飛不起來：

| 條件 | GPU 有效嗎 | 原因 |
|---|---|---|
| batch=1、hidden 768（本範例） | 只有 1.9× | 張量太小，kernel 啟動開銷主導 |
| batch=8、同一模型 | 會明顯變好 | 8 條序列的矩陣乘可以合併，張量變大 |
| hidden 2048 以上（1.5B/2.9B） | 會明顯變好 | 單次矩陣乘的計算量追上啟動開銷 |
| chunk 拉很大 | 沒用 | RWKV 的時間維度本質上序列，拉長只是多跑幾輪 |

**真正能讓 GPU 發揮的是 batch，不是 chunk。** 這跟 Transformer 的直覺相反：
Transformer 你拉長序列就能把 GPU 餵飽（一次矩陣乘算完所有位置），
RWKV 拉長序列只是多跑幾次迴圈。要餵飽它，得同時跑多條**獨立的序列**。

代價是 `State` 要準備 N 份（每條序列一份），而且 `forward` 目前寫死 batch=1。
要做就得改模型——這是文件三第 4 節那種等級的工程。

所以現階段的實務建議：

```text
① 先用 GPU 跑 chunk=8（1.9× 免費加速，零改動）
② 覺得不夠快，再考慮 LoRA（固定成本從 5.7 GB 掉到 1 GB 以下，chunk 能開大）
③ 真要靠 GPU 吃飯，就得改模型支援 batch，那是另一個專案
```

還有一件事值得記住：**GPU 版的 loss 與 CPU 版到小數第四位都一致**
（7.3661 vs 7.3660）。所以你在 GPU 上調出來的超參數，搬到 CPU 上照樣有效，
反之亦然。這比「快幾倍」更實用——它意味著你不需要為了換裝置重跑實驗。

## 7. LoRA：數學、實作、以及為什麼必須改模型

### 7.1 數學

微調時的權重變化 ΔW 本身是低秩的（Aghajanyan 等人 2020 的實驗結果）。
所以不用存整個 ΔW，存兩個小矩陣就夠：

```text
y = x·W₀ᵀ + (x·Aᵀ)·Bᵀ · (α/r)

W₀ : (out, in)  凍結，不訓練
A  : (r, in)    可訓練
B  : (out, r)   可訓練
α/r: 縮放係數
```

參數量從 `in × out` 降到 `r × (in + out)`。768×768 在 r=4 時是 6144，**1.04%**。

兩個關鍵設計：

- **B 初始化為 0**，所以初始時 ΔW = B·A = 0，模型行為與原模型完全一致。
  這是 LoRA 最重要的性質：接上去不會破壞原有能力。
- **α/r 的縮放**，讓改 r 的時候輸出量級不變，超參數才好沿用。

### 7.2 實作

```rust
struct LoraLinear {
    // 凍結的主權重，形狀 (out, in)。刻意用 Tensor 而不是 Var。
    base: Tensor,
    // 低秩分解的下投影，形狀 (r, in)。
    a: Var,
    // 低秩分解的上投影，形狀 (out, r)。
    b: Var,
    // 縮放係數 α/r。
    scale: f64,
}

impl LoraLinear {
    fn forward(&self, x: &Tensor) -> Result<Tensor> {
        // 主路徑：x·W₀ᵀ。因為 base 不是 Var，這條路徑完全不建反傳節點，省記憶體。
        let main = x.matmul(&self.base.t()?)?;
        // 旁路第一段：x·Aᵀ → (n, r)。把 in 維壓到 r 維。
        let low = x.matmul(&self.a.as_tensor().t()?)?;
        // 旁路第二段：(n, r)·Bᵀ → (n, out)。再升回 out 維。
        let delta = low.matmul(&self.b.as_tensor().t()?)?;
        // 乘上縮放係數後與主路徑相加。這是唯一的融合點。
        Ok(main.add(&(delta * self.scale)?)?)
    }

    // 部署時把旁路併回主權重，得到一個普通張量。
    fn merge(&self) -> Result<Tensor> {
        // ΔW = (B·A) · scale，形狀 (out, in)。
        let delta = self.b.as_tensor().matmul(self.a.as_tensor())?;
        Ok(self.base.add(&(delta * self.scale)?)?)
    }
}
```

`05_lora_math.rs` 的實測（768×768，真實增量的秩固定為 4，訓練 300 步）：

```text
r=2   可訓練參數    3072（ 0.52%）  最終 MSE = 7.866e-3
r=4   可訓練參數    6144（ 1.04%）  最終 MSE = 2.195e-5
      合併後與目標權重的最大差異 = 4.40e-2
r=8   可訓練參數   12288（ 2.08%）  最終 MSE = 7.160e-6
      合併後與目標權重的最大差異 = 3.77e-2
r=32  可訓練參數   49152（ 8.33%）  最終 MSE = 8.103e-5
      合併後與目標權重的最大差異 = 3.69e-2
```

- **r=2 學不動**（7.87e-3，比 r=4 差 358 倍）——真實秩是 4，低秩投影表達不了。
- **r=4 就夠了**（2.20e-5），r=8 再好一點點（7.16e-6）。
- **r=32 反而變差**（8.10e-5）——參數變多，同樣 300 步訓練不足。
  實務上這代表「r 不是越大越好」，要用驗證集 loss 決定。
- 業界慣例是 **r=8~16**（Qwen / Llama 微調社群的值），這組數字正好解釋了為什麼。

### 7.3 為什麼在 candle 裡 LoRA 特別麻煩

PyTorch 可以 `replace_module(model, 'att.receptance', lora_layer)` 就地換掉一層。
candle 沒有這種反射機制。翻開 `rwkv_v7.rs`：

```rust
pub struct Model {
    embeddings: Embedding,
    blocks: Vec<Block>,
    ln_out_weight: Tensor,   // ← 是 Tensor，不是 Var
    ln_out_bias: Tensor,
    head_t: Tensor,          // ← 載入時就 .t().contiguous() 固定了佈局
    pub version: ModelVersion,
}
```

權重是 `Tensor` 不是 `Var`，而且載入時就轉置＋複製成特定佈局。
你沒辦法在外部「插入」一個旁路。

**要對 rwkv_v7 做真正的 LoRA，只有一條路：改模型原始碼。** 改動點共 6 處：

| 位置 | 現在的型別 | 要換成 | 形狀 |
|---|---|---|---|
| `Block.att.receptance_t` | `Tensor` | `LoraLinear` | [768, 768] |
| `Block.att.key_t` | `Tensor` | `LoraLinear` | [768, 768] |
| `Block.att.value_t` | `Tensor` | `LoraLinear` | [768, 768] |
| `Block.att.output_t` | `Tensor` | `LoraLinear` | [768, 768] |
| `Block.ffn.key_t` | `Tensor` | `LoraLinear` | [3072, 768] |
| `Block.ffn.value_t` | `Tensor` | `LoraLinear` | [768, 3072] |

注意 `_t` 後綴：candle 在載入時就做了 `.t()?.contiguous()`，
所以這些欄位存的是**轉置後**的權重。改的時候要跟著改 `forward` 裡的 `matmul` 方向，
否則形狀會對不上——這是實際改的時候最容易錯的地方。

改完之後，`Model::new` 要接受一個「要不要套 LoRA」的參數，
並且把 `LoraLinear` 的 `a`/`b` 收集成一個 `Vec<Var>` 回傳給呼叫者。

> **替代方案：凍結式微調（selective fine-tuning）**
> 不改模型，把所有參數都建成 Var，但只把「最後 4 層 + head」交給優化器。
> 這不是 LoRA（沒有低秩約束，梯度仍然算全部參數），但一行都不用改模型，
> 適合先驗證「資料有沒有問題、loss 會不會動」。
> 實作只要一行：`let vars = varmap.all_vars().into_iter().skip(N).collect();`

**這也是為什麼 mistral.rs 這種專案要自己重寫一份模型。**
不是為了炫技，是因為要做 ISQ 與 LoRA，就必須在模型裡留下「可插拔」的縫。
candle-transformers 的定位是「參考實作 + 推論」，不是訓練框架。

## 8. 存檔與載入

```rust
// 存：直接寫 safetensors，key 就是原本的張量名。
varmap.save("rwkv7-0.1b-ft.safetensors")?;

// 載：原樣讀回來，形狀與名字都對得上。
let mut varmap2 = VarMap::new();
// load 會「新增」變數，這跟 set 不一樣——load 是給空 VarMap 用的。
varmap2.load("rwkv7-0.1b-ft.safetensors")?;
```

三個實務建議：

1. **只存有變化的參數。** 全量微調存 728 MB，但如果你只動了最後 4 層，
   可以只 `save` 那 4 層的 Var。LoRA 更是只有幾 MB。
2. **存 BF16 省一半空間。** `varmap.save` 存的是當前 dtype，
   想省空間就在存之前把 Var 轉 BF16（但記得訓練時要 F32）。
3. **留一份原始權重的校驗和。** 微調最容易出的災難是「不小心把原模型覆蓋掉」，
   然後你永遠不知道是微調變差還是檔案壞了。

## 9. 與 DeepSeek、Qwen 的連線

### LoRA 的 rank 該選多少

本文實測的結論（r=8~16）在 Qwen / Llama 上同樣成立，
但有一個關鍵差異：**模型的隱藏維度越大，同一個 r 的「相對表達力」越弱**。

- 0.1B（hidden 768）：r=8 已經很夠。
- Qwen2.5-7B（hidden 3584）：社群慣例 r=16~64。
- DeepSeek-V3（hidden 7168）：全量微調不現實，LoRA 通常 r=64~128。

直覺解釋：LoRA 的容量是 `r × (in + out)`，而「需要改動的子空間維度」
大致隨 hidden 成長。所以 r 要跟著放大，但不是線性放大。

### 為什麼 DeepSeek 的 MLA 讓 LoRA 更複雜

DeepSeek-V2/V3 用 MLA（Multi-head Latent Attention），KV 被壓到一個低秩潛空間。
MLA 本身**已經是低秩分解**，你在上面再套一層 LoRA，等於「低秩的低秩」。
實務上的兩個後果：

1. **MLA 的 `kv_a_proj` / `kv_b_proj` 不適合套 LoRA**，因為它已經是壓縮過的表示，
   再壓會失去表達力。通常只對 `q_proj`、`o_proj`、`gate/up/down_proj` 套。
2. **MoE 的 expert 要不要一起微調？** 通常不動 expert，只微調 shared expert 與 attention。
   理由跟文件一第九節一樣：每個 expert 太小，微調容易過擬合。

### Qwen 微調的兩個實務差異

1. **Qwen 用 tied embedding**（`tie_word_embeddings=true`），
   所以 `embed_tokens` 與 `lm_head` 是同一個張量。
   微調時如果你只更新 head，embedding 也會跟著變——這點在 RWKV-7 上不成立
   （它的 `emb` 與 `head` 是兩個獨立張量，各 50.3M 參數）。
2. **Qwen 有 chat template**。你的 RWKV-7 語料是裸文字，但 Qwen 微調必須套
   `<|im_start|>user\n...<|im_end|>` 這種格式，否則 loss 會收斂到很奇怪的地方。
   這是「格式錯誤」而不是「模型不會」，新手最容易卡在這。

## 10. 練習

1. **把 `chunk` 從 8 加到 64**，觀察三件事：每步耗時、loss 震盪幅度、顯存（用 `nvidia-smi`）。
   驗證「RWKV 的顯存不隨長度成長」這句話。
2. **實作凍結式微調**：只把 `blocks.8~11` 與 `head` 交給優化器，其他參數不傳。
   比較 loss 曲線與全量微調的差異。
3. **把 `VarmapBackend` 改成「可切換精度」的版本**：
   `get` 時把 BF16 權重轉 F32 回傳，`get_unchecked` 時回傳原始 BF16。
   這樣 1.5B 有機會塞進 6 GB。
4. **寫一個 LoRA 版的 `Block`**，只改 `receptance` 一處，跑 10 步確認梯度有到 `a`/`b`。
   這是你之後 fork 整個模型的第一步。
