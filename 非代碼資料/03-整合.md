## 0. 一句話結論，附證據

**candle 的量化張量（`QTensor`）不能反向傳播。不是「不好用」，是根本沒有梯度。**

證據一，`QTensor::dequantize` 回傳的張量明確斷開計算圖：

```rust
// candle-core/src/quantized/mod.rs:689
pub fn dequantize(&self, device: &Device) -> Result<Tensor> {
    let storage = self.storage.dequantize(self.shape.elem_count())?;
    // BackpropOp::none() —— 這個張量沒有父節點，backward 到它就停了。
    let none = crate::op::BackpropOp::none();
    crate::tensor::from_storage(storage, self.shape.clone(), none, false).to_device(device)
}
```

證據二更直接，`QMatMul` 的前向函式名字就叫「**不要反向**」：

```rust
// candle-core/src/quantized/mod.rs:1021
fn forward(&self, xs: &Tensor) -> Result<Tensor> {
    match self {
        // apply_op1_no_bwd = apply op 1, no backward。
        Self::QTensor(t) => xs.apply_op1_no_bwd(t.as_ref()),
        // 反觀純張量的分支，用的是會建圖的 matmul。
        Self::Tensor(w) => { /* ... */ xs.matmul(&w) }
    }
}
```

所以：**`QMatMul` 可以用來推論，不能用來訓練。**
你沒辦法對一個 Q4_K 權重求梯度，因為那個 kernel 從頭到尾沒打算寫 backward。

---

## 1. 為什麼會這樣

不是 candle 偷懶，是**量化 GEMM 的 backward 在數學上很麻煩**。

前向是 `y = x · dequant(W)`。如果要對 W 求梯度，得先有 `∂y/∂W`，
而 `dequant(W)` 是一個階梯函數（把整數乘上 scale），它的導數幾乎到處是 0。
這就是 QAT（quantization-aware training）要引入 STE（straight-through estimator）的原因——
用「假裝導數是 1」的方式繞過去。

llama.cpp / ggml 從一開始就只做推論，所以完全沒寫這部分。
candle 的 `quantized` 模組是照 ggml 的語意實作的，自然也沒有。

**實務上的三個後果**：

1. 你不能「拿一個 Q4_K 模型直接微調」。
2. 但你可以「拿一個 Q4_K 模型當**凍結的底座**」，只訓練旁邊的 F32 小參數——
   這就是 QLoRA，而 candle 缺的是「把旁路接上去」的縫。
3. 你也可以「先反量化回 F32 再微調」，代價是顯存回到全量微調的水準。

## 2. 三條路線

| 路線 | 主體精度 | 可訓練參數 | 0.1B 顯存 | 1.5B 顯存 | 實作難度 | candle 支援 |
|---|---|---|---|---|---|---|
| A. 先壓後訓 | F32（反量化回來） | 全部 | **5926 MiB（實測）** | 不可能 | ★ | 原生可跑 |
| B. 凍結量化 + 旁路 | Q8_0/Q4_K | LoRA（幾 MB） | ~1 GB（推算） | ~3 GB（推算） | ★★★ | 要自己接 |
| C. QAT / ISQ | 訓練中量化 | 全部或 LoRA | 視設計 | 視設計 | ★★★★ | 要重寫 |

> 路線 A 的 0.1B 是**實測值**（RTX 3050 6 GB，`nvidia-smi` 採樣峰值 5926 MiB），
> 不是估算。路線 B 因為 candle 還沒有 `quantized_rwkv_v7`，沒有可跑的實作，
> 數字是「Q8_0 主體 + 活化 + 少量 adapter 狀態 + 配置器碎片」推算出來的，
> 請當作量級參考，不要當精確值。

對你這台 6 GB 的機器，實際可選的是：

- **0.1B**：只有 A 實測跑通（chunk 上限 8）。B 理論上更省，但要先寫出模型。
- **1.5B**：只有 B 有機會。F32 主體是 6.1 GB，直接爆；Q8_0 主體是 1.6 GB，
  扣掉配置器碎片與活化值後還有約 3 GB 餘裕。
- **2.9B**：candle 根本沒有 `quantized_rwkv_v7`，連推論都不行，見第 6 節。

## 3. 路線 A：先壓後訓（可跑）

流程很直白：**GGUF → 反量化成 F32 → 塞進 VarMap → 照文件二的迴圈訓練**。

```rust
// 1. 讀 GGUF 的 header（只讀中繼資料，不載入張量）。
let mut file = BufReader::new(File::open("rwkv7-0.1b-q8_0.gguf")?);
let content = gguf_file::Content::read(&mut file)?;

// 2. 逐個張量反量化，組成一個普通的 HashMap<String, Tensor>。
let mut tensors: HashMap<String, Tensor> = HashMap::new();
for name in content.tensor_infos.keys() {
    // 讀成 QTensor（此時還是壓縮狀態）。
    let qt = content.tensor(&mut file, name, &dev)?;
    // 反量化回 F32。注意這一步之後就跟量化無關了。
    let t = qt.dequantize(&dev)?;
    tensors.insert(name.clone(), t);
}

// 3. 之後完全照文件二的流程：填 VarMap → 建模型 → 訓練。
// （這裡的 tensors 已經是 F32，不需要再 to_dtype。）
```

**這條路的意義在哪？** 對 0.1B 來說幾乎沒有——BF16 → Q8_0 → F32 只是一次有損來回。
但對真實場景很有用：

- 你從網路上抓到一個 Q4_K_M 的模型，作者沒放原始權重。
- 你想在這個基礎上微調，接受「從 4 bit 反量化回來的權重」當起點。
- 精度會比原始 BF16 差一點，但如果你只是要「在這個模型的知識基礎上加一點東西」，
  通常夠用。

**代價**：反量化之後顯存就回到全量微調的水準，Q4_K 省下來的空間全部還回去。
所以路線 A 本質上是「用量化換下載時間，不換訓練成本」。

> **一個實測細節**：Q8_0 反量化幾乎無損（文件一量到 RMSE 0.0053），
> 所以「Q8_0 起點 + 全量微調」是安全的。Q4_K 的 RMSE 是 0.0744，差一個數量級，
> 從 Q4_K 起點微調要有心理準備。

## 4. 路線 B：凍結量化主體 + F32 旁路

這是真正的 QLoRA 思路，也是唯一能讓 1.5B 在 6 GB 上動起來的路。

### 4.1 資料流

```text
        ┌──────────────────────────────┐
        │  Q8_0 權重（凍結，只讀）        │  ← QMatMul::forward，無梯度
        └──────────────┬───────────────┘
                       │ y_main
   x ──────────────────┼──────────────► + ──► y
                       │ y_delta
        ┌──────────────┴───────────────┐
        │  F32 旁路 A(768×8) B(768×8)   │  ← 普通 Tensor 運算，有梯度
        └──────────────────────────────┘
```

關鍵在於：主路徑走 `QMatMul`（省顯存、無梯度），旁路走普通 `matmul`（有梯度）。
兩條路在最後相加，梯度只會流到旁路。

### 4.2 為什麼 candle 需要「混合 backend」

問題回到文件二的 `VarmapBackend`。那時候所有參數都是 `Var`。
現在我們要的是「**有些參數是 `Var`（旁路），有些是 `QTensor`（主體）**」。

`SimpleBackend::get` 回傳的是 `Tensor`，而 `QTensor` 不是 `Tensor`——
中間隔著一個 `dequantize`。所以如果你在 `get` 裡直接 `dequantize`，
就等於路線 A（顯存爆掉），完全失去意義。

**真正可行的做法是改模型，不是改 backend。** 把 `Block` 裡的權重型別從
`Tensor` 換成一個 enum：

```rust
/// 一個「可能是量化、可能是浮點」的線性層。
/// 量化分支走 QMatMul（無梯度、省顯存），浮點分支走普通 matmul（有梯度）。
enum MaybeQuantLinear {
    /// 凍結的量化權重。用於 1.5B / 2.9B 這種塞不進 F32 的模型。
    Quantized(QMatMul),
    /// 可訓練的浮點權重。用於 0.1B 或 LoRA 旁路。
    Float(Tensor),
}

impl MaybeQuantLinear {
    fn forward(&self, x: &Tensor) -> Result<Tensor> {
        match self {
            // 走量化 GEMM。這條路不建反傳節點，顯存只算輸出。
            Self::Quantized(q) => q.forward(x),
            // 走普通 matmul。注意要先轉置，因為 candle 存的是 (out, in)。
            Self::Float(w) => x.matmul(&w.t()?),
        }
    }
}
```

然後 `Block` 的六個 `_t` 欄位改成 `MaybeQuantLinear`，
`Model::new` 多一個參數決定要讀 GGUF 還是 safetensors。

**這就是 fork。** 沒有別的辦法——candle 的模型是寫死的，沒有 hook。

### 4.3 顯存帳（1.5B，6 GB 卡）

| 項目 | 大小 | 說明 |
|---|---|---|
| Q8_0 主體 | 1.6 GB | `rwkv7-g1d-1.5b` 量化後約 1.6 GB |
| LoRA 旁路（r=16，6 個矩陣 × 24 層） | ~9 MB | 24 × 6 × 16 × (2048+2048) × 4 B |
| 旁路梯度 + AdamW | ~27 MB | 旁路參數的 3 倍 |
| 活化值 | 每 token 約 40 MB | **隨 chunk 線性成長**，不是固定值 |
| CUDA context | ~500 MB | 驅動自己吃的 |
| 配置器碎片 | ~900 MB | 實測 0.1B 時看到的量級 |
| **合計（chunk=32）** | **約 4.3 GB** | 還有約 1.8 GB 餘裕，chunk 大概能到 64~96 |

對照：同樣的 1.5B 走 F32 全量微調要 6.1 GB（光主權重），直接爆。

> **這張表是推算的，不是實測的**——因為 candle 沒有 `quantized_rwkv_v7`，
> 目前沒有可跑的實作。我用 0.1B 的實測結果（第 6.2 節）來校準：
> 那邊固定成本 5.7 GB、活化值每 token 約 25 MB、配置器碎片約 900 MB。
> 1.5B 的活化值按 hidden 2048/768 的比例放大到每 token 約 40 MB。
> 兩個數字都說明同一件事：**活化值是隨 chunk 成長的，「狀態固定大小」只在推論成立。**

### 4.4 一個容易忽略的細節：輸出頭的精度

LoRA 通常只套在 attention 與 FFN 上，但 **`head`（輸出投影）建議留 F32 或至少 Q6_K**。
原因：head 直接決定 logits，量化誤差不會被任何東西平均掉。
文件一量到 `emb + head` 佔 0.1B 檔案的 60.1%，看起來很浪費，
但那 60.1% 換來的是「模型不會胡說八道」。

如果你真的想省，折衷方案是 **head 留 Q6_K、emb 留 Q4_K**——
embedding 是查表，誤差會被後面的 LayerNorm 與注意力稀釋一部分。

## 5. 路線 C：QAT 與 ISQ

### QAT（量化感知訓練）

在訓練時就模擬量化誤差，用 STE 讓梯度穿過 `round()`：

```text
前向：  w_q = round(w / scale) * scale        ← 有量化誤差
反向：  ∂L/∂w ≈ ∂L/∂w_q                       ← 假裝導數是 1（STE）
```

好處是模型「學會在有量化誤差的情況下工作」，量化後掉點最少。
壞處是要從頭訓練或至少大量微調，而且 candle 完全沒有支援——
你得自己寫 `round` 的 backward。

### ISQ（In-Situ Quantization）

這是 **mistral.rs** 專案提出的做法，思路跟 QAT 相反：

1. 載入 FP16 模型。
2. 對每個張量算「量化誤差」，如果誤差太大就自動降級到更高精度（混合精度量化）。
3. 量化是「就地」的，不需要校準資料集。

它解決的是「我不知道該給這個張量幾 bit」這個問題——
文件一第七節的 `pick_dtype` 是手寫規則，ISQ 是自動決策。

為什麼 mistral.rs 做得到而 candle 做不到？因為它自己重寫了所有模型，
每個 `Linear` 都是它自己的 `QLinear`，可以隨時換精度。
這又回到同一句話：**要在模型裡留縫**。

## 6. 自己補一個 quantized_rwkv_v7

這是本文最實際的一節。你手上有一份 **2.9B Q8_0 GGUF，candle 跑不動**，
因為 `candle-transformers` 有 `quantized_rwkv_v5`、`quantized_rwkv_v6`，就是沒有 v7：

```text
candle-transformers-0.11.0/src/models/
├── quantized_rwkv_v5.rs     ← 有
├── quantized_rwkv_v6.rs     ← 有
├── quantized_rwkv_v7.rs     ← 沒有
├── rwkv_v7.rs               ← 只有浮點版
└── quantized_qwen3.rs       ← 連 Qwen3 都有
```

### 6.1 對照 `quantized_rwkv_v6.rs` 的差異

v6 的量化版結構是：

```rust
// 大概長這樣（v6 的寫法）。
pub struct Model {
    // 詞嵌入用 QTensor，因為查表需要特殊處理（每個元素只有半個位元組）。
    embeddings: QTensor,
    // 每一層。
    blocks: Vec<Block>,
    // 輸出頭，量化成 QMatMul。
    head: QMatMul,
}
```

v7 要改的地方只有三類：

| v7 的張量 | v6 的對應 | 量化後怎麼處理 |
|---|---|---|
| `emb.weight` [65536, c] | `emb.weight` | `QTensor::embedding(&ids)` |
| `head.weight` [65536, c] | `head.weight` | `QMatMul`，注意要轉置 |
| `att.receptance/key/value/output` [c, c] | 同名 | `QMatMul` |
| `ffn.key` [4c, c] / `ffn.value` [c, 4c] | 同名 | `QMatMul` |
| `att.w1/w2`、`a1/a2`、`v1/v2`、`g1/g2` | 同名 | **保持 F16**（太小，量化不划算） |
| `att.x_r/x_w/...` [1,1,c] | 同名 | **保持 F32** |
| `att.r_k` [n_heads, 64] | 同名 | **保持 F32** |

### 6.2 一個關鍵的坑：轉置

`rwkv_v7.rs` 在載入時就做了轉置：

```rust
// 浮點版是這樣存的。
let receptance_t = vb.get((c, c), "receptance.weight")?.t()?.contiguous()?;
```

因為它前向時是 `xs.matmul(&receptance_t)`，而 `xs` 是 `(1, c)`。
但 `QMatMul::forward` 內部**已經自己處理了轉置**：

```rust
// candle-core/src/quantized/mod.rs:1024
Self::Tensor(w) => {
    // 注意這行：內部會 .t()。
    let w = match *xs.dims() { /* ... */ _ => w.t()? };
    xs.matmul(&w)
}
```

所以你在量化版裡**不能再手動轉置**，否則會變成「轉置兩次」。
這個坑很隱蔽——形狀檢查會過（`(c,c)` 轉置後還是 `(c,c)`），
但算出來的結果是錯的，而且不會報錯。

**驗證方法**：拿同一份權重，分別用浮點版與你的量化版跑 `forward_seq`，
比對 logits 的最大絕對差。Q8_0 的話應該在 1e-2 以內；差到 1 以上就是轉置錯了。

### 6.3 名稱映射

文件一第八節列出了 candle 與 llama.cpp 的命名對照。要讀 llama.cpp 的 GGUF，
必須先寫一層映射：

```rust
/// 把 llama.cpp 的張量名轉成 candle 的名字。
/// 只處理 `blk.N.` 這種帶層號的，其餘直接對應。
fn llama_name_to_candle(name: &str) -> Option<String> {
    // 全域張量，直接查表。
    let global = match name {
        "token_embd.weight" => "emb.weight",
        "output.weight" => "head.weight",
        "output_norm.weight" => "ln_out.weight",
        "output_norm.bias" => "ln_out.bias",
        "token_embd_norm.weight" => "blocks.0.ln0.weight",
        "token_embd_norm.bias" => "blocks.0.ln0.bias",
        // 其他（含 tokenizer 相關）不回傳。
        _ => "",
    };
    if !global.is_empty() {
        return Some(global.to_string());
    }

    // 帶層號的：拆成 blk / N / 其餘。
    let rest = name.strip_prefix("blk.")?;
    let (idx, tail) = rest.split_once('.')?;
    // 尾段查表。
    let mapped = match tail {
        "attn_norm.weight" => "ln1.weight",
        "attn_norm.bias" => "ln1.bias",
        "attn_norm_2.weight" => "ln2.weight",
        "attn_norm_2.bias" => "ln2.bias",
        "time_mix_ln.weight" => "att.ln_x.weight",
        "time_mix_ln.bias" => "att.ln_x.bias",
        "time_mix_receptance.weight" => "att.receptance.weight",
        "time_mix_key.weight" => "att.key.weight",
        "time_mix_value.weight" => "att.value.weight",
        "time_mix_output.weight" => "att.output.weight",
        "time_mix_w0.weight" => "att.w0",
        "time_mix_w1.weight" => "att.w1",
        "time_mix_w2.weight" => "att.w2",
        "time_mix_a0.weight" => "att.a0",
        "time_mix_a1.weight" => "att.a1",
        "time_mix_a2.weight" => "att.a2",
        "time_mix_v0.weight" => "att.v0",
        "time_mix_v1.weight" => "att.v1",
        "time_mix_v2.weight" => "att.v2",
        "time_mix_g1.weight" => "att.g1",
        "time_mix_g2.weight" => "att.g2",
        "time_mix_k_k.weight" => "att.k_k",
        "time_mix_k_a.weight" => "att.k_a",
        "time_mix_r_k.weight" => "att.r_k",
        "channel_mix_key.weight" => "ffn.key.weight",
        "channel_mix_value.weight" => "ffn.value.weight",
        // lerp_fused 要拆成六個 x_*，這裡先跳過（見下面的說明）。
        _ => return None,
    };
    Some(format!("blocks.{idx}.{mapped}"))
}
```

**注意那個 `time_mix_lerp_fused`。** llama.cpp 把六個 `[1,1,c]` 的向量
拼成一個 `[c,1,1,6]` 張量。你要在載入時把它拆開：

```rust
// 形狀是 [c, 1, 1, 6]，六個通道分別對應 x_r/x_w/x_k/x_v/x_a/x_g。
let fused = content.tensor(&mut file, "blk.0.time_mix_lerp_fused.weight", &dev)?;
let fused = fused.dequantize(&dev)?.reshape((c, 6))?;
for (i, suffix) in ["x_r", "x_w", "x_k", "x_v", "x_a", "x_g"].iter().enumerate() {
    // 取第 i 欄，形狀 (c,)。
    let v = fused.narrow(1, i, 1)?.squeeze(1)?;
    // 再 reshape 成 (1,1,c)，跟 candle 期待的形狀一致。
    out.insert(format!("blocks.0.att.{suffix}"), v.reshape((1, 1, c))?);
}
```

這個拆分順序（r, w, k, v, a, g）是從 llama.cpp 的 `rwkv7.cpp` 對出來的，
寫錯不會報錯，只會讓模型輸出變得莫名其妙。**這是整個任務裡最容易出錯的一步。**

**速度我沒有實測數據，所以不給 tok/s 數字。** 但可以給你一個可驗證的推算框架：

```text
理論解碼速度上限 ≈ 記憶體頻寬 ÷ 每步要讀的權重位元組
```

- RTX 3050 Laptop：192 GB/s
- 0.1B Q8_0（170 MiB）：192e9 / 178e6 ≈ **1000 tok/s 上限**
- 0.1B Q4_K（131 MiB）：≈ **1400 tok/s 上限**
- 2.9B Q8_0（3.03 GiB）：≈ **63 tok/s 上限**

實際會低很多（kernel launch、注意力、取樣都會吃時間），
但這個框架很好用：**它告訴你「換更低的量化」什麼時候還有意義**。
當你的實測速度已經接近上限的 70%，再壓位元數的收益就很小了，該去優化別的地方。

> 你自己跑一下就有數字了：
> `ollama run shoumenchougou/rwkv7-g1k:2.9b --verbose` 會印出 eval rate。

## 8. 與 DeepSeek、Qwen 的連線

### 8.1 DeepSeek 的 FP8：為什麼它敢在訓練時就量化

DeepSeek-V3 用 FP8 做訓練（不只是推論），關鍵是 **per-block scaling**：
每個 128×128 的區塊有自己的縮放係數，而且前向與反向都用同一套。

跟本文的對照：
- 我們在文件一做的 Q4_K 是 **per-256-element 區塊**，比 DeepSeek 的 128×128 粗得多。
- DeepSeek 的 FP8 是 8 bit 浮點（有指數位），動態範圍比 int8 大得多，
  所以能用「一個區塊一個 scale」而不會爆。
- 這也解釋了為什麼 DeepSeek 能在 H800 上訓練 671B——FP8 讓頻寬需求砍半。

### 8.2 Qwen 的 W4A16：量化的是權重，不是活化值

Qwen 社群的 AWQ / GPTQ 量化都是 **W4A16**：權重 4 bit，活化值 16 bit。
為什麼不把活化值也壓？因為活化值有離群值（ outlier），
壓到 4 bit 會直接毀掉（回到文件一第四節的實驗：per-tensor 4bit 讓正常權重全部歸零）。

AWQ 的核心觀察跟本文的 imatrix 是同一件事：
**不是所有權重都一樣重要，按「活化值的大小」加權，就能保住關鍵通道。**
實作上 AWQ 會在量化前先做一次「通道縮放」，把重要的通道放大、不重要的縮小，
讓 4 bit 的解析度集中在重要的地方。

### 8.3 為什麼 candle 做不了真正的 QLoRA

QLoRA 的三個支柱：

1. **NF4 量化**（4-bit NormalFloat，針對常態分佈最優化的量化格點）— candle 沒有。
2. **Double quantization**（連縮放係數都再量化一次）— candle 沒有。
3. **Paged optimizer**（顯存不夠時把優化器狀態丟到 CPU）— candle 沒有。

candle 只有 ggml 的 K-quant 系列，那是為**推論**設計的，不是為訓練設計的。
所以你在 candle 上做 QLoRA，只能做到「凍結量化主體 + F32 旁路」，
沒有 NF4 帶來的額外精度優勢。

**這不是缺點，是定位差異。** candle 的目標是「用 Rust 跑推論，順便提供訓練原語」，
不是「取代 PyTorch」。知道邊界在哪，比硬套一個不存在的功能有用。

### 8.4 如果你真的要做 QLoRA，該用什麼

| 需求 | 工具 |
|---|---|
| 在 6 GB 上微調 1.5B | candle + 路線 B（本文），或 llama.cpp 的 LoRA 訓練 |
| 在 6 GB 上微調 7B | 必須 QLoRA → `bitsandbytes` + PEFT（PyTorch） |
| 只想跑推論 | candle（浮點）或 Ollama（GGUF） |
| 想學原理 | 就是這三份文件 |

**llama.cpp 本身有 LoRA 微調功能**（`llama-finetune`），走的是路線 B 的變體，
而且它已經處理好名稱映射與量化主體。如果你只是想「快點微調一個 GGUF」，
那條路比在 candle 裡重寫模型快得多。但如果你想**理解**為什麼要這樣做，candle 逼你看清楚每一層。
